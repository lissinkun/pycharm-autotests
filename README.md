# Учебный проект API-тестирования

Автоматизированные тесты REST API на Python с pytest и requests.
Текущий этап: Allure-отчёт, API-клиент, фикстуры и параметризация тестов пользователей JSONPlaceholder.
Четыре тестовые функции дают семь отдельных тестовых случаев.

## Что проверяем

| Сценарий | Запрос | Ожидаемый статус |
| --- | --- | --- |
| Список пользователей | GET /users | 200 |
| Существующие пользователи | GET /users/1, /users/2, /users/3 | 200 |
| Несуществующие пользователи | GET /users/0, /users/999999 | 404 |
| Создание пользователя | POST /users | 201 |

Кроме HTTP-статусов проверяем содержимое JSON: поля, значения и типы данных.

Используем https://jsonplaceholder.typicode.com — публичное учебное API без ключа.
POST лишь имитирует создание: запись не сохраняется на сервере.
Поэтому тест создания проверяет ответ POST и не пытается читать запись отдельным GET.
Описание поведения: https://jsonplaceholder.typicode.com/guide/.

## Запуск в Windows PowerShell

Требуется Python 3.10 или новее. Из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest -v
```

Если команда `python` недоступна, для создания окружения укажи полный путь
к установленному python.exe. Активация окружения не требуется: команды явно
используют Python из `.venv`.

Запуск одного теста:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_users.py::test_get_existing_user -v
```

Зависимости ограничены совместимыми диапазонами версий; это ещё не lock-файл.

## Как устроен тест

1. Подготавливаем адрес и, для POST, данные запроса.
2. Отправляем запрос через метод `users_client`, который использует HTTP-сессию.
3. Проверяем HTTP-статус с помощью `assert`.
4. Преобразуем JSON-ответ в Python-объект методом `response.json()`.
5. Проверяем содержимое ответа.

`json=payload` преобразует словарь Python в JSON и задаёт соответствующий
Content-Type. `timeout=10` ограничивает ожидание соединения и чтения;
это не общий лимит длительности теста.

pytest находит файлы `test_*.py` и функции `test_*`. Если условие `assert`
ложно, тест завершается ошибкой, а pytest показывает причину.

## Структура

```text
tests/test_users.py  — запросы и проверки
tests/conftest.py    — общие фикстуры: адрес API, HTTP-сессия и клиент
clients/users_client.py — методы запросов к API пользователей
clients/__init__.py  — обозначает пакет clients
settings.py         — адрес API и таймаут из переменных окружения
requirements.txt    — зависимости
pyproject.toml      — правила проверки и форматирования Ruff
pytest.ini          — папка поиска тестов и параметры вывода
.gitignore          — локальные файлы, исключённые из Git
```

Тесты не зависят от порядка запуска. Фикстуры передают настройки из `settings.py`
в API-клиент.

## Настройки окружения

`settings.py` читает переменные окружения при импорте, до выполнения тестов:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `API_BASE_URL` | `https://jsonplaceholder.typicode.com` | Базовый адрес API |
| `API_TIMEOUT` | `10` | Таймаут соединения и чтения, в секундах |

Без этих переменных достаточно обычной команды запуска. Чтобы изменить
настройки в текущем терминале PowerShell перед запуском:

```powershell
$env:API_BASE_URL = "https://jsonplaceholder.typicode.com"
$env:API_TIMEOUT = "5"
.\.venv\Scripts\python.exe -m pytest -v
```

Переменные окружения содержат строки. `float()` преобразует таймаут в число;
используй положительное конечное значение, например `5` или `2.5`.
Нечисловое значение приведёт к ошибке при загрузке настроек.
Изменение адреса не адаптирует сценарии и ожидаемые данные к другому API.
Файл `.env` автоматически не загружается, дополнительные библиотеки не нужны.

Вернуть значения по умолчанию, удалив переменные из текущего терминала:

```powershell
Remove-Item Env:API_BASE_URL -ErrorAction SilentlyContinue
Remove-Item Env:API_TIMEOUT -ErrorAction SilentlyContinue
```

## Фикстуры

Фикстура — функция подготовки данных или ресурсов для теста, отмеченная
декоратором `@pytest.fixture`. pytest автоматически находит фикстуры
в `tests/conftest.py`: импортировать их в тестовый модуль не нужно.

В записи `def test_get_users(users_client):` аргумент соответствует имени
фикстуры. Перед запуском теста pytest подготавливает её зависимости
`base_url` и `api_session`, создаёт клиент и передаёт его в функцию теста.

- `base_url` возвращает адрес API. `scope="session"` означает, что фикстура
  выполняется один раз за весь запуск pytest.
- `api_session` создаёт `requests.Session()` — объект для HTTP-запросов,
  который может сохранять cookies и повторно использовать соединения.
  Без явного `scope` действует `function`: каждый тест получает новую сессию,
  поэтому cookies и настройки сессии не переходят между тестами.
- `yield session` передаёт сессию тесту. После завершения теста, в том числе
  при падении проверки, pytest продолжает фикстуру после `yield`, и
  `session.close()` освобождает её соединения.

Посмотреть этапы подготовки и завершения фикстур:

```powershell
.\.venv\Scripts\python.exe -m pytest -v --setup-show
```

## Параметризация

`@pytest.mark.parametrize` запускает одну тестовую функцию с разными данными.
В тесте существующего пользователя строка `"user_id, expected_name, expected_email"`
задаёт имена аргументов, а каждый кортеж в списке — значения для одного запуска.
`ids` задаёт понятные подписи случаев в выводе pytest.

`users_client` приходит из фикстуры. `user_id`,
`expected_name` и `expected_email` приходят из параметризации.
Каждый случай получает собственную `api_session` и отдельный результат:
падение одного не мешает выполнению остальных при обычном запуске.

Ожидаемые имена и email указаны в тесте явно. Мы не получаем их отдельным
запросом к тому же API, иначе могли бы сравнивать ошибочные данные с ними же.

Запуск конкретного набора данных (кавычки сохраняют квадратные скобки):

```powershell
.\.venv\Scripts\python.exe -m pytest "tests/test_users.py::test_get_existing_user[user-2]" -v
```

## API-клиент

`UsersClient` объединяет методы `get_users()`, `get_user(user_id)` и
`create_user(payload)`. В нём находятся пути запросов и таймаут (10 секунд
по умолчанию). Конструктор `__init__` сохраняет адрес, HTTP-сессию и таймаут
в атрибутах конкретного объекта; `self` обозначает этот объект.

Методы возвращают исходный `requests.Response`. Проверки статусов и JSON
остаются в тестах. Клиент не вызывает `raise_for_status()`, поэтому тесты
могут проверять и ожидаемые ответы 404.

Фикстура `users_client` создаёт отдельный клиент для каждого тестового случая.
HTTP-сессию закрывает её собственная фикстура `api_session` после выполнения
теста. Запускай тесты из корня проекта командой `python -m pytest`, используя
Python из `.venv`, как показано выше.

## Качество кода: Ruff

Ruff устанавливается из `requirements.txt` в окружение проекта.
Настройки находятся в `pyproject.toml`: целевая версия Python 3.10,
длина строки для форматтера 88, базовые проверки ошибок и порядка импортов.

Проверки без изменения файлов:

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Автоматическое исправление доступных безопасных замечаний и форматирование:

```powershell
.\.venv\Scripts\python.exe -m ruff check . --fix
.\.venv\Scripts\python.exe -m ruff format .
```

Точка означает текущую папку проекта. Ruff автоматически исключает `.venv`.
Его служебный кэш `.ruff_cache/` исключён из Git. Ruff анализирует исходный код;
для проверки поведения API по-прежнему нужен запуск pytest.

## Allure-отчёт

Python-плагин `allure-pytest` сохраняет результаты тестов. Он устанавливается
из `requirements.txt`. Отдельная программа Allure CLI строит из них сайт;
для Allure CLI 2 нужна Java. На текущем компьютере обе программы уже установлены.
Проверка доступности: `allure --version` и `java -version`.

```powershell
.\.venv\Scripts\python.exe -m pytest -v
allure serve reports/allure-results
```

Первая команда запускает тесты. В `pytest.ini` указаны
`--alluredir=reports/allure-results` (папка результатов) и
`--clean-alluredir` (удалить прежние результаты из этой папки перед запуском).
Поэтому отчёт содержит только последний запуск, без накопления старых случаев.

Вторая команда генерирует отчёт и открывает локальный сайт в браузере.
Оставь терминал работающим, пока смотришь отчёт. `Ctrl+C` останавливает сервер.
Раздел Suites содержит тесты, шаги запросов и проверок, параметры, длительность
и вложения: метод, URL, отправленные JSON-данные, HTTP-статус и тело ответа.
При сетевой ошибке ответ отсутствует, но запрос и исключение остаются в отчёте.
В учебных вложениях сохраняются тела целиком; для API с секретами понадобится
маскировать чувствительные данные перед прикреплением.

Чтобы отдельно сохранить сайт и затем открыть его:

```powershell
allure generate reports/allure-results -o reports/allure-report --clean
allure open reports/allure-report
```

Не открывай `index.html` двойным щелчком: интерфейсу Allure нужен HTTP-сервер,
который запускают `serve` или `open`. Прежний `reports/report.html` относится
к pytest-html и больше не обновляется. Папка `reports/` исключена из Git.

Для запуска нужен интернет. Недоступность сервиса, прокси или проблемы TLS
могут приводить к ошибкам тестов и требуют отдельной диагностики.
